# 51. 変更管理・復旧の基本設計

## 全体構成

このパックは、[12. 構築の基本設計](12-build-design.md)・[41. セキュリティ強化の基本設計](41-security-design.md)と同じ「**作る**役目と**確かめる**役目を分ける」設計に、「**戻す**役目」を加えます。

```text
利用者
  ├─ snapshot_config.sh --config FILE [--label NAME] [--execute] ── 変更前の状態を保存
  │       └─ scripts/lib/common.sh（ログ、検証、終了コード）
  ├─ change_deploy.sh --config FILE --source DIR [--execute] ── 変更本体
  │       ├─ 1) snapshot_config.sh を内部で呼び出す（変更前スナップショット）
  │       ├─ 2) SOURCE の内容を CHANGE_TARGET へ適用する
  │       ├─ 3) VERIFY_CMD（既存の受け入れ試験）を検証ゲートとして実行する
  │       └─ 4) 検証ゲートが失敗した場合、restore_config.sh を自動的に呼び出す
  └─ restore_config.sh --config FILE --snapshot DIR [--execute] ── 復元
          └─ 復元後、manifest.txt のチェックサムと突き合わせて一致を確認する
```

`snapshot_config.sh`と`restore_config.sh`は単独でも実行できます（`change_deploy.sh`を使わずに、手動での変更の前後で明示的に呼ぶ運用も可能です）。`change_deploy.sh`はこの2本を組み合わせ、検証ゲートによる自動判定を追加したものです。

## `backup.sh`を再利用しなかった理由（設計判断）

[50. 変更管理・復旧案件概要](50-change-project-overview.md)の「`backup.sh`との違い」で要約したとおり、`backup.sh`の`SOURCE_DIR`/`BACKUP_DIR`/`RETENTION_DAYS`という設定形状は、このパックの用途に対して次の3点で不足していました。

1. **対象が単一ディレクトリ前提であること。** `backup.sh`は`SOURCE_DIR`という1つのディレクトリを`tar.gz`にまとめます。しかし変更管理で保存したい対象は、`/etc/nginx/sites-enabled`・`/etc/ufw`・`/etc/sudoers.d/90-opsadmin`のように、**複数の独立した絶対パス**にまたがります。`SOURCE_DIR`を複数回呼び出す方式も検討しましたが、それでは「1回の変更に対応する1つのスナップショット」という単位が保てず、復元時にどのアーカイブとどのアーカイブを組み合わせればよいか分からなくなります。
2. **保持方針が異なること。** `backup.sh`の`RETENTION_DAYS`は「一定期間残して古いものを消す」という継続的な世代管理を前提にしています。変更管理のスナップショットは「次の変更まで、あるいは切戻しが完了するまで残っていればよい」性質のもので、自動削除の設計思想がそもそも異なります（本パックでは自動削除を行わず、保持・削除の判断は運用者に委ねます）。
3. **復元時に要求する保証が異なること。** `backup.sh`の復元は「`tar -xzf`で展開できればよい」という手動の作業を前提にしています。一方、変更管理の復元は「切戻しが完了した」と機械的に言い切るために、**復元後のチェックサムがスナップショット時点と一致すること**を`restore_config.sh`自身が確認する必要があります。この確認ロジックは`backup.sh`には存在せず、後付けすると`backup.sh`の責務（単純な世代バックアップ）を超えてしまいます。

以上から、**共通ライブラリ（`scripts/lib/common.sh`）は共有しつつ、スクリプト自体は無理に統合せず新規に実装しました。** これは[41. セキュリティ強化の基本設計](41-security-design.md)が採用した「作る役目と確かめる役目を分ける」設計判断と同じ考え方で、「継続的なデータ保全」と「変更ごとのロールバック」という異なる責務を1本のスクリプトに詰め込まないことを優先しています。

## スナップショットの保存形式

`snapshot_config.sh`は、`SNAPSHOT_TARGETS`の各絶対パスを、元のパス構造を保ったまま`<SNAPSHOT_DIR>/<label>_<timestamp>/payload/`配下へミラーします（例: `/etc/nginx/sites-enabled`は`payload/etc/nginx/sites-enabled`として保存されます）。これは`tar`でまとめるより展開の手間が少なく、`restore_config.sh`が「元のパスへそのままコピーし直す」という単純な操作で復元できるようにするためです。

スナップショットディレクトリには次の3ファイルを置きます。

| ファイル | 内容 |
|---|---|
| `payload/` | `SNAPSHOT_TARGETS`の各対象を元のパス構造のままミラーしたコピー |
| `targets.txt` | スナップショット時点の`SNAPSHOT_TARGETS`（1行1パス） |
| `manifest.txt` | `payload/`配下の全ファイルの`sha256sum`（`restore_config.sh`が復元後の比較に使う） |

`SNAPSHOT_TARGETS`に存在しない対象（まだ作成されていない設定ファイル等）が含まれていても、スナップショット自体は失敗させず、警告として記録して続行します（`provision_web_server.sh`が`ufw`未導入時にWARNで続けるのと同じ「フェイルソフト」の方針）。

## 変更適用フローと切戻し基準

`change_deploy.sh`は次の順序で処理し、各段階の結果に応じて挙動を変えます。

```text
1. スナップショット（snapshot_config.sh を内部呼び出し）
2. 変更の適用（SOURCE の内容を CHANGE_TARGET へ追加・上書き。削除の反映は行わない）
3. 検証ゲート（VERIFY_CMD を実行）
     ├─ 終了コード 0 → 確定（何もしない。切戻しコマンドをログに残すのみ）
     ├─ 終了コード 1 → 警告。自動切戻しはしない（人による go/no-go 判断が必要）
     └─ 終了コード 2以上 → 不合格。restore_config.sh を自動的に呼び出して切戻す
```

**終了コード1（警告）で自動切戻ししない理由**は、`build_verify.sh`・`verify_hardening.sh`の終了コード1は「警告はあるが致命的ではない」状態（例: ufw未導入で確認できないだけ）を表すためです。これを機械的に「壊れた」と判定して毎回切戻すと、警告付きでも許容できる変更まで自動的に巻き戻され、かえって運用の柔軟性を損ないます。終了コード2以上（`EXIT_ERROR`）は、既存パックの規約上「入力や状態が明確に不正」を意味するため、これだけを自動切戻しの引き金にします。

### 切戻し基準表

| 条件 | 種別 | 判定方法 | 挙動 |
|---|---|---|---|
| `VERIFY_CMD`の終了コードが2以上 | 自動 | `change_deploy.sh`が終了コードを直接判定 | `restore_config.sh`を自動的に呼び出し、復元後にチェックサム一致を確認する |
| `VERIFY_CMD`の終了コードが1（警告） | 人による判断 | 同上 | 変更は維持したまま`EXIT_WARNING`で終了し、切戻しコマンドをログに提示する。実施者・承認者が内容を見て判断する |
| HTTPヘルスチェック失敗（`build_verify.sh`のHTTP応答確認） | 自動（`VERIFY_CMD`経由） | `build_verify.sh`内でHTTP応答が200以外ならWARNを1件加算し、他の警告と合わせて終了コードに反映される | 他の警告と合算した結果が2以上になることは現状の`build_verify.sh`の設計では無い（警告は常に終了コード1に丸められる）ため、**HTTP応答の失敗単独では自動切戻しされない**。単独で自動切戻しの引き金にしたい場合は、[10. サーバー構築ポートフォリオへの発展計画](10-server-build-roadmap.md)の今後の課題として、`VERIFY_CMD`にHTTPヘルスチェックだけを厳格に判定する専用コマンド（終了コード2を返すラッパー）を指定する運用を想定する |
| サービス起動失敗（`systemctl is-active`が失敗） | 人による判断（現状） | `build_verify.sh`・`verify_hardening.sh`はサービス停止をWARN（終了コード1）として扱う | 上記と同じ理由で、現状は自動切戻しの対象外。重大度を上げたい場合は、専用の`VERIFY_CMD`ラッパーで終了コード2を返すよう変更する |
| 変更ウィンドウの超過、承認の不在 | 人による判断 | スクリプトでは検知しない（運用手順の遵守が前提） | [50. 変更管理・復旧案件概要](50-change-project-overview.md)の「変更ウィンドウと承認者」に従い、実施者が中断し、承認者に報告する |

**この表の設計上の限界を隠さず明記します。** 現状の`build_verify.sh`・`verify_hardening.sh`は「警告点の数にかかわらず、1件でもあれば終了コード1」という設計のため、`change_deploy.sh`から見ると「軽微な警告」も「複数の重大な問題」も同じ終了コード1に見えます。より厳密な自動判定（HTTPヘルスチェック失敗だけを即座に不合格にする、等）が必要な場合は、`VERIFY_CMD`に専用の判定ラッパーを指定することで対応できますが、そのラッパー自体は本パックには含まれていません。

## 復元と復元試験（diffで証明する）

`restore_config.sh`は、単に`cp`が成功したことをもって「復元完了」とはしません。復元後、`manifest.txt`に記録されたスナップショット時点のチェックサムと、復元先の実ファイルのチェックサムを1つずつ再計算して突き合わせます。

- 一致すれば`OK`、不一致であれば`WARN`として記録し、最終的な終了コードにも反映します（1件でも不一致があれば`EXIT_WARNING`）。
- 復元先にファイルが存在しない場合も同様に警告として記録します。

これにより、「`cp`コマンドが正常終了コードを返した」という弱い保証ではなく、「復元後の内容がスナップショット時点と一致する」という強い保証を、実行のたびに機械的に確認できます。[43. セキュリティ強化テスト仕様](43-security-test-plan.md)や[14. 構築テスト仕様](14-build-test-plan.md)が「コマンドの成功」だけでなく「結果の中身」を確認する設計を踏襲したものです。

## セキュリティ設計

- `snapshot_config.sh`は読み取りとコピーのみを行い、`backup.sh`と同様にroot権限を必須にしません（対象パスの読み取り権限があれば実行できます）。ただし`--execute`を明示しない限り何も作成しません。
- `restore_config.sh`・`change_deploy.sh`は、`/etc`配下など実システムの設定へ書き込む可能性があるため、`provision_web_server.sh`・`harden_server.sh`と同じく`--execute`には常にroot権限を要求し、root以外なら終了コード2で拒否します。
- `SNAPSHOT_DIR`・`SNAPSHOT_TARGETS`・`CHANGE_TARGET`は`require_absolute_safe_path`で、絶対パスであることと重要なシステムディレクトリそのものでないことを確認します。
- `SNAPSHOT_DIR`と`SNAPSHOT_TARGETS`が重なる（互いに配下関係になる）場合は終了コード2で拒否します（スナップショット自身をスナップショット対象に含めてしまう事故を防ぐため）。
- `CHANGE_TARGET`が`SNAPSHOT_TARGETS`に含まれていない場合、`change_deploy.sh`は終了コード2で拒否します（切戻せない変更を実行させないため）。
- `restore_config.sh`は、復元先の絶対パスを`--snapshot`で指定されたスナップショットの`SNAPSHOT_DIR`配下であることを検証したうえで使用し、任意のパスを復元元として受け付けません。
- `VERIFY_CMD`は`config/change.conf`（`load_config`で所有者・書込権限を検証済み）に記述された、実施者が信頼できる文字列であることを前提とし、`bash -c --`で実行します（`eval`は使用しません）。これは既存パックの`ADMIN_SSH_PUBKEY`等と同様に、「設定ファイル自体は信頼済みの入力」という前提に立った設計です。
- 既定の実行は常にドライランで、`--execute`を明示した場合だけ変更を行います。
- `change_deploy.sh`は変更の適用を「追加・上書きのみ」とし、`SOURCE`にないファイルを`CHANGE_TARGET`から削除しません。これは`--delete`付き同期による意図しない削除事故を避けるための意図的な制限です（今後の課題として[10. サーバー構築ポートフォリオへの発展計画](10-server-build-roadmap.md)に記載します）。

## 残るリスク

- `change_deploy.sh`の変更適用は「追加・上書きのみ」であり、削除の反映（同期）には対応していません。削除を伴う変更は、`SOURCE`側に削除後の完全な内容を用意するか、別途手動で対応する必要があります。
- 検証ゲートの終了コード1と2以上の二値判定に依存しており、HTTPヘルスチェック単体・サービス起動失敗単体を自動切戻しの引き金にするには、専用の`VERIFY_CMD`ラッパーが別途必要です（上記「切戻し基準表」参照）。
- 変更ウィンドウ・承認フローはドキュメント上の運用ルールであり、スクリプトによる強制（承認済みチケット番号の入力必須化等）は行っていません。
- 実Ubuntu VMへの適用、実際のnginx設定変更・切戻しの実地確認は`NOT RUN`です（[50. 変更管理・復旧案件概要](50-change-project-overview.md)参照）。

これらは「未実施」であり、実施したかのように書きません。着手する際は[10. サーバー構築ポートフォリオへの発展計画](10-server-build-roadmap.md)の優先度表を参照してください。
