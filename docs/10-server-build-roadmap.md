# 10. サーバー構築ポートフォリオへの発展計画

## 結論

このリポジトリは、要件、設計、実装、テスト、運用、証跡を一続きで学べる点が強みです。一方、現在の中心は**構築後のLinuxサーバーを点検・保守するシェルスクリプト**であり、サーバー構築エンジニアのポートフォリオとしては構築工程の実物が不足しています。

不足を隠さず、次の段階として小さなWebサーバーを再現可能に構築し、このリポジトリの点検・バックアップへ接続すると、初心者にも採用担当者にも学習の流れが伝わります。

## 初心者向けの最小構成

最初からクラウド、DB、冗長化を全部入れません。学習用VMを1台用意し、次の経路だけを完成させます。

```text
手元PC
  └─ SSH / HTTP
       └─ Ubuntu VM
            ├─ firewall
            ├─ nginx
            ├─ 静的なサンプルページ
            ├─ systemd
            └─ 本リポジトリの点検・バックアップ
```

学習環境は外部公開せず、NATまたはホストオンリーネットワークを使います。秘密鍵、パスワード、実IPはリポジトリへ保存しません。

## 推奨する学習順序

### Phase 1: 手作業で仕組みを理解する

1. VMを作り、OS、CPU、メモリ、ディスク、NICを記録する。
2. IPアドレス、デフォルトゲートウェイ、DNSの役割を図にする。
3. Nginxを導入し、設定検査、起動、自動起動、HTTP応答を確認する。
4. 許可する通信をSSHとHTTPに限定し、設定前後を記録する。
5. VM再起動後にもHTTP応答とサービス状態を確認する。

### Phase 2: 自動化して再現性を示す

1. 手順をAnsibleのロールへ分ける。
2. 初期状態のVMに適用し、変更内容を記録する。
3. 2回目の適用で不要な変更が出ないことを確認する。
4. 設定値を変数へ分離し、秘密情報を保管しない。
5. 本リポジトリの監査スクリプトを配置し、構築後試験として実行する。

### Phase 3: 壊して戻す

1. 検証環境で設定誤りを作り、設定検査で停止できるか確認する。
2. サービス停止、ディスク逼迫、バックアップ失敗を1つずつ再現する。
3. 初動、切り分け、復旧、再発防止を障害票に記録する。
4. バックアップを別ディレクトリへ復元し、元データと比較する。

## 各工程で残す証跡

初心者が「できたつもり」にならないよう、各作業を次の5点で1セットにします。

1. **目的:** 何を満たす作業か。
2. **変更:** どのファイルや設定を変えたか。
3. **確認:** 利用者視点を含め、どのコマンドで確認したか。
4. **結果:** 終了コード、差分、ログ、HTTP応答。
5. **復旧:** 失敗時の停止条件と切戻し方法。

証跡には日時、OS、ツールのバージョン、Gitコミット、期待値、実結果、`PASS / FAIL / NOT RUN` を含めます。画面写真だけでなく、再実行できるコマンドとテキストログを優先します。

## 完成判定

次を満たせば、「運用スクリプトを作った」から「小規模Webサーバーを設計・構築し、安全に運用へ引き渡した」ポートフォリオへ発展したと判断できます。

- [ ] 初期状態のVMからREADMEだけで再構築できる。
- [ ] 構成図、パラメータ、ポート、ユーザー、権限の設計根拠がある。
- [ ] 自動化を2回実行し、2回目に意図しない変更がない。
- [ ] 再起動後にSSH、HTTP、サービス自動起動を確認している。
- [ ] 正常系だけでなく、設定誤りとサービス停止を試験している。
- [ ] バックアップの作成だけでなく復元とデータ比較を実施している。
- [ ] 変更前確認、承認、切戻し条件、作業後確認を記録している。
- [ ] 未実施や環境依存の項目を `NOT RUN` と明記している。

## 面接での伝え方

ツール名を並べるより、`要件 → 設計理由 → 自動化 → 試験 → 障害対応 → 残存リスク` の順で1本のストーリーにします。特に、手作業で理解してから自動化した理由、危険な既定値を避けた理由、試験で何を証明できて何を証明できないかを自分の言葉で説明してください。
